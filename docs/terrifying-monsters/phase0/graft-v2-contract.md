# Terrifying Monsters — Graft v2 Contract and Migration Roadmap

**Status:** Phase 0 architectural contract  
**Repository baseline:** `main`, `3f70b1e83a6c4d072a53b900840971a792d0eab1`  
**Package baseline:** `31.1.0a`  
**Runtime changes in this phase:** none  
**UI changes in this phase:** forbidden

## 1. Purpose

Terrifying Monsters already has a capable numerical engine. The work must preserve:

- Monster Frames and their CR targets;
- the 5E 2024 rules model;
- three-round DPR simulation;
- closed-loop CR fitting;
- the effective combat profile;
- export and Run Mode contracts;
- the current Monster Composer interaction model.

The objective is not to replace the engine. It is to give the engine a stronger editorial input model so that a selected graft can describe a recognizable behavior rather than one isolated stat-block line.

The required transition is:

```text
legacy graft
→ one ability
→ generated numerical routine

becomes

Graft v2 concept
→ coherent ability bundle
→ authored tactical routine
→ existing numerical engine
→ recognizable stat block
```

## 2. Non-negotiable UI boundary

No implementation phase before the final public-polish phase may change:

- React components;
- CSS or design-system rules;
- layout, sidebars, stage, bottom bar, navigator, cards, controls, or stat-block presentation;
- current slot selection behavior;
- labels, tooltips, modes, routing, keyboard behavior, drag behavior, or contextual menus.

A Graft v2 still occupies one existing slot and is selected through the existing UI. The model and compiler must adapt behind that contract.

If the new model requires additional information, it must be exposed through internal adapters or derived state. A visible UI change requires explicit approval from Danilo and belongs to the final UI refinement phase.

## 4. Domain definitions

### 4.1 Monster Frame

The encounter and numerical envelope selected by the user.

A Frame includes or derives:

- target CR;
- encounter role;
- tactical role;
- danger profile;
- tempo;
- tier;
- baseline AC, HP, attack bonus, save DC, DPR, initiative and budget;
- caps and fitting constraints.

The Frame answers:

> How powerful and encounter-relevant should this creature be?

It does not define source identity or a complete combat routine.

### 4.2 Chassis

The creature's physical and systemic base.

A Chassis includes or derives:

- creature type and tags;
- body plan and anatomy capabilities;
- size;
- movement modes;
- senses;
- languages;
- innate defensive assumptions;
- valid equipment or natural-weapon assumptions;
- compatibility tokens granted before graft selection.

The Chassis answers:

> What kind of creature can carry these grafts?

### 4.3 Graft

A source-inspired modular concept that modifies the compiled creature.

A Graft may add or modify:

- one or more abilities;
- a tactical routine;
- statistics;
- anatomy tokens;
- compatibility constraints;
- state transitions;
- counterplay;
- complexity and pressure contributions;
- rendering metadata.

A Graft is not required to equal one ability.

### 4.4 Attack Pattern

A specialized Graft defining the creature's offensive behavior.

An Attack Pattern includes:

- an identifiable tactical fantasy;
- a coherent offensive repertoire;
- a default routine;
- one or more conditional deviations;
- legal Multiattack composition or an explicit reason not to use Multiattack;
- target-selection logic;
- counterplay;
- CR, tier, role and tempo suitability.

An Attack Pattern answers:

> What does this monster repeatedly try to accomplish in combat, and how does the party respond?

It is not merely the monster's primary attack.

## 5. Canonical source-of-truth decision

### 5.1 Target direction

The canonical authoring source must become the shared content model contained in Inspiration Modules and Content Packs.

Target flow:

```text
Inspiration Module / Content Pack
→ canonical shared monster component
→ runtime adapter
→ Monster Composer compiler
```

This aligns monster content with the wider Cruor loop:

```text
real source
→ source anchor
→ inspiration module
→ composable component
→ generator
→ table-ready output
```

### 5.2 Current transitional flow

The current system still performs a circular conversion:

```text
monster-grafts.js
→ shared monster component
→ content registry / content pack
→ runtime monster graft
→ merge with monster-grafts.js
```

This remains supported during migration but must not be the final authoring architecture.

### 5.3 Migration rule

There will be no global cutover until a source family is complete.

For each source family:

1. create canonical Graft v2 components in its Inspiration Module or Content Pack;
2. validate full runtime equivalence through the adapter;
3. make the registry version primary for that source;
4. retain the native graft as a compatibility fallback for one migration window;
5. remove or archive the fallback only after coverage and regression gates pass.

After the Phase 1 cutover begins, new public graft content must not be authored only in `monster-grafts.js`.

## 7. Ability bundle contract

### 7.1 Core rule

A Graft v2 may emit zero, one, or multiple abilities.

```text
Graft v2
→ abilities[]
→ flattened Monster Ability Model
```

The existing rules schema remains the language for each individual ability.

The new compiler layer must not duplicate the rules engine. It only expands a Graft v2 into the ability records already understood by the engine.

### 7.2 Stable identifiers

Every emitted ability requires an ID stable within the graft:

```text
<graft-id>:<ability-id>
```

Runtime IDs must remain deterministic across regeneration, export and Run Mode.

### 7.3 Provenance

Every compiled ability must retain:

- source Graft v2 ID;
- source component ID;
- source anchor;
- local ability ID;
- migration origin;
- authored or generated status.

### 7.4 Legacy adapter

A legacy graft without `abilities[]` compiles as a one-entry bundle.

```js
abilities: [buildMonsterAbilityFromGraft(legacyGraft)]
```

This preserves existing behavior until each graft is migrated.

## 8. Attack Pattern editorial contract

### 8.1 Required fields

Every migrated Attack Pattern must define:

- identity;
- repertoire;
- default routine;
- counterplay;
- frame fit;
- complexity intent;
- balance intent;
- migration provenance.

### 8.2 Repertoire rules

The goal is not a fixed action count. The goal is meaningful tactical variety.

Guidance:

- low-CR Minion: one real offensive behavior may be sufficient;
- low-CR Standard: usually one primary action plus one distinct option or rider path;
- mid-CR Standard/Elite: usually two or more distinct actions, with at least one conditional or limited option;
- Boss/Setpiece: broader action economy, off-turn presence, phases or authored alternatives as appropriate.

A repeated copy of the same attack is not a distinct option.

### 8.3 Authored routine rule

Automatic DPR packet splitting remains available as a fallback for legacy content. It must not define the identity of a migrated Attack Pattern.

A migrated Attack Pattern must declare one of:

```text
authored Multiattack
explicit single-action routine
procedure-based routine
non-Multiattack alternating routine
```

### 8.4 Recognition test

Remove the graft title and source label. A reviewer should still be able to recognize the intended creature fantasy from its mechanics.

A pattern fails if the remaining mechanics could belong unchanged to any generic brute, skirmisher or controller.

### 8.5 Coherence test

Each ability must contribute to the same tactical loop.

The pattern fails if its actions are individually thematic but do not form a believable combat behavior.

### 8.6 Counterplay test

A dangerous pattern must give the party readable answers where appropriate:

- deny a lane;
- spread out;
- break an anchor;
- interrupt a state;
- exploit a weakness;
- force movement;
- change damage type;
- spend an action to remove an effect;
- accept a tactical cost.

Counterplay does not reduce Pressure. It measures fairness and response quality separately.

## 9. Structured-rules and text parity contract

### 9.1 Binding rule

For every public ability:

```text
structured rule
= simulated rule
= printed rule
```

No mechanical clause may exist only in `mechanics` prose.

No simulated modifier may be invisible in the printed stat block.

### 9.2 Role of prose fields

Target behavior:

- `summary`: editorial description;
- `counterplay`: editorial explanation backed by structured fields;
- `mechanics`: generated rendering, migration fallback, or editor preview;
- `rules`: canonical mechanical source.

After migration, manual `mechanics` prose must not silently override `rules`.

### 9.3 Known Phase 0 parity candidates

The inventory identifies candidates such as:

- `slam-decomposition`: conditional extra damage die is described in prose but not represented as a structured damage part;
- `skin-slippage`: the grapple-escape advantage clause is present in prose but absent from the structured rule;
- `fresh-bloat-hide`: AC and speed state transition remains coupled to prose and legacy stats;
- `volatile-immobile-mass`: speed, reach and forced-movement resistance need an explicit structural representation.

These examples define the first parity regression fixtures. They are not the only candidates.

## 10. Balance contract

### 10.1 CR remains a power target

CR fitting remains responsible for keeping the final monster within its intended 5E 2024 combat power envelope.

It must continue to evaluate the final compiled ability model and three-round routine.

### 10.2 Build Budget remains a composition constraint

Graft cost and Frame budget control what can be selected.

Build Budget is not Pressure.

### 10.3 Pressure v2

Pressure must be calculated after compilation from the final monster.

Required dimensions:

- attrition;
- spike;
- reliability and target focus;
- control and action denial;
- area and coverage;
- access and tempo;
- off-turn action economy;
- survival pressure.

Pressure must use a normalized public scale independent of Frame graft budget.

### 10.4 Counterplay

Counterplay is a separate measure.

A telegraphed, fair feature may still impose high Pressure. Fairness must never be used as a direct negative Pressure term.

### 10.5 Complexity v2

Complexity must be calculated from the final compiled repertoire:

- number of genuine decisions;
- sequencing requirements;
- conditional branches;
- recharge and resource tracking;
- state tracking;
- summon, object and terrain tracking;
- interactions between abilities;
- off-turn options.

Raw graft count is not sufficient.

### 10.6 Spike Risk

Spike Risk remains separate from average DPR and Pressure.

It must detect:

- concentrated single-target damage;
- first-round burst;
- reliable two-hit downing potential;
- severe save-or-suffer effects;
- stacked off-turn damage;
- conditional damage multiplication.

## 11. Side-override migration contract

The current catalogue stores substantial metadata in exported maps outside the graft objects:

- frame fit;
- compatibility;
- anatomy constraints;
- anatomy grants;
- mechanic metadata.

Graft v2 must absorb these into canonical fields during source-family migration.

Requirements:

- no new source-family content should require a separate override map unless the schema genuinely cannot represent it;
- override entries must resolve to an existing graft ID;
- compatibility tokens require a controlled vocabulary;
- migration must preserve behavior before deleting an override;
- unknown legacy IDs such as `bone-reassembly` must be resolved or explicitly archived.

## 12. Compatibility and rollout strategy

### 12.1 Compiler bridge

The compiler bridge receives mixed content:

```text
legacy grafts + Graft v2 components
```

It emits one unified ability collection and one unified routine model.

### 12.2 No big-bang migration

Migration proceeds source by source:

1. Decomposition;
2. Jikininki;
3. Wolf Spiders;
4. Wax Death Masks.

Each source must pass all gates before the next source becomes canonical.

### 12.3 Existing UI selection contract

The user still selects one entry in the Attack Pattern slot.

Internally that entry may emit several actions. The selected-graft count and slot cap do not need to change.

### 12.4 Existing exports

Export and Run Mode continue consuming the compiled stat block. They must not read Graft v2 objects directly.

## 13. QA gates

### Gate A — Schema

- Graft v2 validates;
- every ability validates against the existing rules schema;
- IDs are deterministic and unique;
- references resolve;
- routine entries resolve to emitted abilities.

### Gate B — Compatibility

- legacy graft output remains unchanged before migration;
- mixed legacy/v2 builds compile;
- current Frame and slot contracts remain intact;
- no UI component requires modification.

### Gate C — Render/simulation parity

- every printed rider is represented structurally;
- every simulated rider is printed;
- damage, conditions, timing, recharge, saves and target count agree;
- generated prose is stable.

### Gate D — Attack Pattern integrity

- no accidental repeated-single-attack Multiattack for migrated patterns;
- every authored routine references valid actions;
- replacement rules are legal;
- limited and recharge options are not repeated illegally;
- pattern passes recognition, coherence and counterplay review.

### Gate E — Balance

- closed-loop CR remains within accepted tolerance;
- three-round DPR remains stable;
- Pressure reacts monotonically to added danger;
- Counterplay does not reduce Pressure;
- Complexity responds to genuine final decision load;
- Spike Risk identifies concentrated burst.

### Gate F — Editorial

- stat block resembles current 5E 2024 editorial conventions;
- the source is recognizable without labels;
- action names and text are concise;
- mechanics do not read as stitched-together graft fragments;
- golden stat blocks receive manual approval.

### Gate G — Public readiness

- unsupported rulesets are hidden;
- development fallbacks do not appear in public output;
- generic legendary fallback actions are removed or blocked;
- printed defenses are valued by the effective profile;
- warnings are treated as failures for the public content set.

## 14. Phased implementation plan

### Phase 0 — Contract and inventory

Deliverables:

- deterministic current-graft inventory;
- Graft v2 contract;
- parity-review candidate list;
- source-of-truth decision;
- migration and QA gates.

No runtime or UI changes.

### Phase 1 — Canonical content boundary

- define the shared Graft v2 schema;
- extend shared component normalization;
- add provenance and migration state;
- prevent circular authority between native graft and registry component;
- retain compatibility adapters.

### Phase 2 — Ability bundle compiler bridge

- compile legacy grafts as one-entry bundles;
- compile Graft v2 `abilities[]`;
- retain stable ability IDs and provenance;
- introduce authored routine model;
- keep current UI consumers unchanged.

### Phase 3 — Parity hardening

- make structured rules authoritative;
- migrate first known text-only riders;
- add render/simulation parity tests;
- block public output when a rider cannot be represented.

### Phase 4 — Pressure, Complexity and Spike Risk v2

- calculate metrics from final compiled output;
- separate Build Budget, Pressure, Complexity, Counterplay and Spike Risk;
- retain old metrics only as migration diagnostics until cutover.

No UI display changes in this phase.

### Phase 5 — Attack Pattern migration

Per source family:

- inventory current offensive concepts;
- consolidate or split legacy actions into coherent patterns;
- author repertoire and routine;
- calibrate by CR, role, tier and tempo;
- approve golden examples.

### Phase 6 — Other graft families

- Body;
- Mind;
- Movement;
- Twist;
- Weakness / Tell;
- Death;
- Lair;
- Horror.

They may emit multiple abilities or modify pattern hooks where justified.

### Phase 7 — Public hardening

- full QA suite;
- Bestiary distribution comparison;
- public content warnings as failures;
- remove placeholders and unsupported public options;
- editorial review of representative builds.

### Phase 8 — UI refinement

Begins only after explicit approval.

Possible goals, not approved changes:

- reveal the repertoire produced by a graft;
- distinguish Build Budget from Pressure;
- communicate Complexity, Counterplay and Spike Risk;
- let users understand the pattern without increasing visible clutter.

## 15. Phase 0 exit criteria

Phase 0 is complete when:

- the generated inventory runs and passes `--check`;
- the complete 90-graft CSV and JSON are available;
- Attack-slot limitations are explicitly documented;
- source-of-truth direction is fixed;
- Graft v2 semantics are fixed;
- compatibility and UI boundaries are fixed;
- implementation order and QA gates are fixed;
- no runtime or UI behavior has changed.
